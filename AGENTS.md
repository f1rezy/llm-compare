# Инструкции для AI-агентов

Инструкции действуют для всего репозитория LLM Compare.

## Проект и структура

LLM Compare позволяет отправлять один запрос нескольким языковым моделям и сравнивать ответы. Монорепозиторий использует npm workspaces и TypeScript.

| Путь                    | Назначение                                                 |
| ----------------------- | ---------------------------------------------------------- |
| `frontend/src/ui/`      | Компоненты React и их CSS Modules                          |
| `frontend/src/hooks/`   | Состояние интерфейса и управление запросами                |
| `frontend/src/api/`     | Вызовы API backend                                         |
| `backend/src/routes/`   | HTTP-обработчики и валидация входных данных                |
| `backend/src/services/` | Работа с внешним AI Proxy                                  |
| `backend/src/pkg/`      | HTTP-утилиты, конфигурация окружения, ошибки и логирование |
| `backend/src/config/`   | Конфигурация маршрутов                                     |
| `common/src/types/`     | Общие контракты API                                        |
| `common/src/utils/`     | HTTP-утилиты для frontend                                  |

- Frontend: React, Vite, TypeScript. Backend: встроенный `node:http`, запуск TypeScript через `tsx`, логирование через Pino.
- Общий пакет импортируется через `@llm-compare/common` и предоставляет исходники TypeScript без отдельной сборки.
- Перед работой читай затрагиваемые файлы и проверяй `git status`. Сохраняй существующие изменения пользователя.
- Сверяй документацию с исходниками и `package.json`: README может отставать от реализации. Не считай описанную как отсутствующую функцию нереализованной без проверки кода.

## Правила реализации

- Следуй существующему стилю, настройкам TypeScript, ESLint, Prettier и `.editorconfig`.
- Используй существующие типы и утилиты. Не дублируй контракты backend и frontend, не скрывай ошибки типов через `any` или необоснованные приведения.
- При изменении API согласованно обновляй контракт в `common`, обработчик backend и вызывающий код frontend. Экспортируй новые общие сущности через существующие `index.ts`.
- Выбирай простое решение в рамках текущей архитектуры. Новая абстракция должна решать конкретную задачу.

### Frontend

- Разрабатывай интерфейс mobile-first: базовые стили для узкого экрана, расширения через media queries.
- Используй CSS Modules (`*.module.css`) для стилей компонентов; глобальные стили держи в `frontend/src/index.css`.
- Выноси вызовы backend в `src/api`, управление состоянием и запросами — в хуки, отображение — в компоненты.
- Для JSON-запросов к BFF используй `fetchJSON` и проверяй поле `success`. Потоковые ответы читай через `fetchResponse` в `frontend/src/api/generation.ts`. Сетевые ошибки и ошибки разбора обрабатывай в вызывающем коде.
- Сохраняй обработку состояний загрузки, ошибки, пустых данных и успешного результата.
- Для генерации сохраняй независимые состояния колонок, отмену запросов и защиту от устаревших ответов. Состояние колонки привязывается к её ID, а не к ID модели.
- Используй семантические элементы, подписи полей и доступные с клавиатуры элементы управления.

### Backend и внешнее API

- Backend выступает BFF: frontend обращается к `/api`, а взаимодействие с AI Proxy находится в `backend/src/services/ai-proxy.ts`.
- Для запросов к AI Proxy используй стандартный `fetch` с проверкой HTTP-статуса и таймаутом. Общие HTTP-обёртки предназначены для frontend.
- Валидируй пользовательские данные на backend. Для JSON-ответов сохраняй формат `{ success: true, data }` или `{ success: false, error }` и существующее разделение HTTP-ошибок и ошибок AI Proxy.
- Сохраняй проверки событий NDJSON при чтении потока AI Proxy. Для обычных успешных JSON-ответов отдельная схема валидации сейчас не используется.
- Конфигурацию получай через существующий `BackendEnv`. Не раскрывай содержимое `.env`, ключи и заголовки авторизации в ответах, логах или frontend-коде.
- Не перезаписывай локальный `.env`. В `.env.example` допускаются только примеры без настоящих секретов.

### Потоковая генерация и метрики

- Интерфейс отправляет отдельный запрос `POST /api/stream` для каждой колонки. `POST /api/generate` возвращает ответ целиком. Оба маршрута используют общую валидацию тела запроса в `backend/src/pkg/generate-request.ts`.
- Используй общий тип `GenerateStreamEvent` из `common` для событий `text-delta`, `finish` и `error`. До отправки заголовков возвращай ошибку HTTP в JSON. После начала потока передавай ошибку событием NDJSON. Поток без `finish` или `error` считается оборванным.
- При закрытии клиентского соединения отменяй запрос BFF к AI Proxy. При остановке генерации сохраняй весь текст, который успела получить активная колонка, и уже завершённые результаты. Повтор запроса после ошибки запускай только для выбранной колонки.
- Измеряй время до первого непустого фрагмента и до завершения ответа на frontend. Стоимость рассчитывай на backend по последним полученным тарифам и доступным счётчикам. В интерфейсе сохраняй нулевые значения и показывай отметки самого быстрого и самого дешёвого ответа только при наличии хотя бы двух сопоставимых результатов для соответствующей метрики.

## Команды и проверка изменений

Команды выполняются из корня репозитория. Используй npm и существующий `package-lock.json`.

| Команда                  | Назначение                           |
| ------------------------ | ------------------------------------ |
| `npm ci`                 | Установка зависимостей по lock-файлу |
| `npm run dev:backend`    | Запуск backend в режиме разработки   |
| `npm run dev:frontend`   | Запуск Vite                          |
| `npm run lint`           | Проверка ESLint во всех пакетах      |
| `npm run typecheck`      | Проверка типов во всех пакетах       |
| `npm run build:frontend` | Проверка типов и сборка frontend     |
| `npm run format:check`   | Проверка форматирования проекта      |

- Для проверки отдельного пакета используй `npm run lint -w @llm-compare/<пакет>` и `npm run typecheck -w @llm-compare/<пакет>`, где пакет — `frontend`, `backend` или `common`.
- После изменений кода запускай линтер и проверку типов затронутых пакетов. При изменении общих контрактов проверяй все пакеты; при изменении frontend проверяй также сборку.
- Для изменений только в документации достаточно проверки форматирования затронутых файлов.
- Форматируй только затронутые файлы. Не запускай массовое исправление проекта ради локальной задачи.
- Скрипт `test` сейчас не настроен. Не заявляй о прохождении тестов, которых нет. При необходимости описывай или выполняй подходящий ручной сценарий проверки.
- При изменении потоковой генерации проверяй постепенный вывод Markdown, остановку с сохранением текста, ошибку отдельной колонки и её повтор. Для проверки с AI Proxy выбирай недорогие модели, учитывай лимит токена и указывай, когда ответы были имитированы.
- Если проверка не прошла, отделяй проблемы своей правки от ранее существовавших. Сообщай о недоступных проверках и причинах.
